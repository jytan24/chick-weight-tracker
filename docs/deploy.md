# Putting JY Chick online (Render + Neon)

This is a step-by-step guide for the first deploy. It uses two free services:

- **Neon** keeps the database (the saved weighings and the login).
- **Render** runs the website.

The code and settings are already prepared (`render.yaml` and the production settings in `config/` and `start/env.ts`). What is left are the steps that need **your own accounts**, so only you can do them.

## Before you start

- [ ] `node ace test`, `npm run typecheck` and `npm run lint` all pass on your PC.
- [ ] Your work is merged into the branch Render will deploy (for example `main`), and that branch is on GitHub. Render reads the code from GitHub.
- [ ] You have a GitHub, a Neon and a Render account (all free, no card needed for these plans).

## Step 1: Create the database on Neon

1. Sign in at neon.tech and create a **project**. Pick the **Singapore** region (closest to Malaysia).
2. Open the project's **Connection details**. Choose the **Parameters only** view (not the long connection string).
3. Write down these four values. You will paste them into Render in Step 2:

| Neon shows | Render setting |
| :--- | :--- |
| Host (looks like `ep-xxxx.ap-southeast-1.aws.neon.tech`) | `DB_HOST` |
| Role / user | `DB_USER` |
| Password | `DB_PASSWORD` |
| Database (usually `neondb`) | `DB_DATABASE` |

Use the **direct** host, not the one with `-pooler` in its name. The migrations run on startup and work best on a direct connection.

## Step 2: Create the website on Render

1. Sign in at render.com and choose **New → Blueprint**.
2. Connect your GitHub repo and pick the branch. Render reads `render.yaml` and shows a service called `jy-chick`.
3. Render asks for the four values marked `sync: false`. Paste the Neon values from Step 1.
4. Click **Apply**. The first build takes a few minutes.

Everything else is already set by `render.yaml`:

| Setting | Value | Why |
| :--- | :--- | :--- |
| `NODE_ENV` | `production` | Turns on secure cookies and refuses to start without `DB_PASSWORD` |
| `TZ` | `Asia/Kuala_Lumpur` | So "today" in the Add form is your sister's today |
| `DB_SSL` | `true` | Neon only accepts encrypted connections |
| `TRUST_PROXY_HOPS` | `1` | Render sits in front of the app. This lets the login limiter see each visitor's real address |
| `APP_KEY` | generated by Render | Signs the login cookie. Never share it and never change it (everyone would be logged out) |
| `SESSION_DRIVER` | `cookie` | The login lives in an encrypted cookie, so no session table is needed |
| `LIMITER_STORE` | `memory` | Login attempt counts are kept in memory (they reset when the app restarts) |

The database tables are created automatically each time the app starts (`migration:run` in the start command). Running it again when nothing changed does nothing.

## Step 3: Create your sister's login

There is no sign-up page. You create her account with a command, from your PC, pointed at the Neon database. **Do this after the first deploy has finished**, because the deploy creates the tables.

In PowerShell, in the project folder (replace the values with your Neon ones):

```powershell
$env:DB_HOST = "ep-xxxx.ap-southeast-1.aws.neon.tech"
$env:DB_USER = "your-neon-role"
$env:DB_PASSWORD = "your-neon-password"
$env:DB_DATABASE = "neondb"
$env:DB_SSL = "true"
node ace create:user sister@example.com
```

It asks for a password (typing is hidden). Pick a long one. Close that PowerShell window afterwards so the Neon password does not stay in memory.

The same command **resets the password** of an existing email, which is how you handle "I forgot my password".

## Step 4: Check it from a phone

Use **mobile data**, not your Wi-Fi, so you know it works from outside your home.

- [ ] Open `https://jy-chick.onrender.com` (use the address Render shows). The first visit may take 30 to 60 seconds, because free services sleep when unused.
- [ ] You land on the login page. Opening `/weighings` without logging in sends you back to login.
- [ ] Log in with your sister's email and password.
- [ ] Add a weighing: Ross, day 21, 0.950 kg. You see **-6.1%** and **Slightly behind**.
- [ ] Edit it, then delete it.
- [ ] Log out.
- [ ] Check the pages are comfortable at phone width and the colours are readable in sunlight.

## Deploy checklist

**Before**
- [x] Tests, typecheck and lint pass (36 tests)
- [x] Migrations tested: they ran, and rolled back, from a production-mode build
- [x] The production build starts and answers `/login` with status 200 and the security headers (HSTS, frame blocking)
- [x] No secrets in git (`.env` is ignored, Render generates `APP_KEY`)
- [ ] Code is on GitHub on the branch Render deploys
- [ ] Neon project and Render service created (Steps 1 and 2)

**During**
- [ ] Watch the Render **Logs** tab until you see `started HTTP server`
- [ ] If the build fails, read the last red lines of the log, they usually name the missing setting

**After**
- [ ] Phone check from mobile data (Step 4)
- [ ] Send your sister the link and her email
- [ ] Tell her the first open of the day can take up to a minute

**Roll back if**
- The site shows an error page after a deploy, or login stops working. Fix: in Render, open the **Events** tab and **Rollback** to the last good deploy. The database is not affected, because we only add tables in this first version.
- A new migration breaks the data. Fix: run `node ace migration:rollback` against Neon from your PC (same settings as Step 3), then roll back the code.

## Things to know

- **Free Render sleeps.** After about 15 minutes idle it stops. The next visit wakes it (30 to 60 seconds). Upgrading to the Starter plan (about US$7 a month) removes this, with no code change.
- **Login lasts 2 hours.** After that she logs in again.
- **Login attempts are limited** to 10 per 15 minutes per address. Because the counts live in memory, they reset when the app sleeps or restarts.
- **Backups.** Neon keeps a short history of the database on the free plan. For longer safety, export the data from the Neon dashboard now and then.
- **Dependency warnings.** `npm audit` reports 22 low or moderate issues, all inside the AdonisJS framework packages, none high or critical. They are fixed by upgrading AdonisJS, not by changing our code. Check again when you next update.
- **Why `TRUST_PROXY_HOPS` is `1`.** If it is too low, the limiter may treat many visitors as one address (safe, but it can lock her out sooner). If it is too high, a visitor could fake their address. After the first deploy, if she gets "too many attempts" much sooner than expected, the number may need to be `2`.
